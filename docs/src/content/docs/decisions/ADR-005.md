**Date**: 2026-07-04
**Status**: Decided

## Context

Agents author screens in protopane (the bootstrap-protopane-project flow) and originally drove the raw HTTP API. Exposing the app over the Model Context Protocol makes that flow discoverable and typed, but a second entry point must not become a second implementation.

## Decision

The MCP server is one more inbound adapter: streamable HTTP mounted at `/mcp` on the same FastAPI app, stateless, with its session manager in the app lifespan. Tools mirror the container's use cases one-to-one. Tools returning domain data serialize through the HTTP DTO mappers; `delete_project`, `delete_scheme`, `delete_screen` and `delete_template` return `{"deleted": "<slug>"}`, naming the removed item. The same fail-closed Basic auth gates the mount (ADR-002). The `bootstrap-project` prompt packages the design-session runbook. The in-page design chat has no MCP counterpart: an MCP client is itself the authoring agent.

## Rationale

- Every write takes the identical path through the core regardless of door, so invariants (like the token gate, ADR-006) hold once for all clients.
- One deployable and one credential story; no drift between an "API" and an "agent API".
- The tool list derives from the container wiring, so capability reporting is honest by construction.

## Alternatives considered and rejected

- **A sidecar MCP service wrapping the REST API**: a second deployable that can drift, with its own auth and its own serialization; forbidden by the platform's inbound-adapter pattern.
- **Exposing the design chat as an MCP tool**: nests one agent inside another for no capability gain; the connected agent already holds the authoring loop.
