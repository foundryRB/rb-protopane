**Status**: Decided

## Context

Protopane holds one project per customer engagement: a token set and a handful of screens, edited in bursts during live design sessions by a single operator. The persistence layer must survive pod restarts, be trivially backed up, and never corrupt a project mid-write.

## Decision

Each project is one JSON document at `<projects-dir>/<slug>/project.json` on a PersistentVolumeClaim, written atomically (write-then-rename). The Deployment uses the `Recreate` strategy so at most one pod ever writes the volume.

## Rationale

- The data is small, low-frequency, and document-shaped; a project loads and saves as one unit, which a single file models exactly.
- Backup and restore are file copies; the operator can read a project with any editor.
- Atomic writes make a crash mid-save leave either the old file or the new one, never a torn one.
- `Recreate` eliminates the two-writers window a rolling update would open on the shared volume.

## Alternatives considered and rejected

- **PostgreSQL**: right for concurrent writers and relational queries, both absent here; it would add an instance dependency to a tool whose value is being always ready for a session.
- **SQLite**: solves atomicity but hides projects in an opaque file, losing the copy-a-folder operability for zero added capability at this scale.
