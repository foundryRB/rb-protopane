**Status**: Decided

## Context

Protopane serves the design phase, before a customer code repository exists. Once a real frontend is built, two artifacts describing the same UI exist: the prototype and the production code. Anything that must be kept in sync by hand will drift.

## Decision

The prototype is a reference, not a contract. The export (`GET /api/projects/<slug>/export`) yields the theme as a `:root` token block and the screen bodies; the tokens drop into the real frontend unchanged, the markup informs the component build. After handoff, the prototype is discarded, not maintained alongside the frontend.

## Rationale

- Parallel-maintained copies drift by design; declaring the prototype disposable removes the temptation to treat it as a second source of truth.
- The token set is the durable output: it ports losslessly because both sides speak the same shadcn token names.
- Screens keep their value as a visual record of what the customer approved, without any claim to correctness after the build starts.

## Alternatives considered and rejected

- **Round-trip sync with the real frontend** (regenerate screens from production components): mechanical-sounding, but the mapping is lossy in both directions and the maintenance burden lands on every frontend change forever.
- **Prototype as the contract** (frontend must match it pixel-for-pixel): inverts ownership; the frontend owns state, data, and correctness the prototype knows nothing about.
