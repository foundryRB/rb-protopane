**Date**: 2026-07-04
**Status**: Decided

## Context

Protopane's value rests on one rule: screens are themed exclusively through design tokens, so markup carries no literal colors. A literal never reskins with the brand and breaks at handoff. The rule lived in documentation while every door (UI, REST, MCP) would happily persist violations, and the block vocabulary the rule depends on was duplicated between the frontend bundle and the pattern docs.

## Decision

The rule is a gate in the save use cases. Screen and template saves whose markup carries a literal color (hex, `rgb()`, numeric `hsl()`) are rejected with the violation report; theme saves must carry exactly the canonical token set with well-formed values. Because the gate lives in the use cases, it binds every door identically. The block vocabulary moves server-side and is served at `/api/blocks` and as the `list_blocks` tool; the editor's style manager carries no color properties, so the UI cannot produce what the gate rejects.

## Rationale

- A documented convention decays; a gate with a self-explaining rejection report teaches every caller, human or agent, at the moment of the mistake.
- Serving the vocabulary removes the hand-maintained copy (the pattern doc had already drifted from the real palette) and lets agents discover the instance's actual blocks.
- Restricting the style manager aligns the tool's own UI with its thesis: colors come from tokens, never per-element styling.

## Alternatives considered and rejected

- **Warn-only linting**: the report without the teeth; off-token markup would still persist and surface as a broken retheme in front of the customer.
- **Client-side validation only**: leaves REST and MCP ungated, splitting behavior per door, which the platform's adapter rules forbid.
